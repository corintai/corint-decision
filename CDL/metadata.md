# CDL Metadata (compatibility)

<!-- cdl-scope: compatibility-unverified -->
> This page is an unverified compatibility reference. Its snippets are not Core support evidence.
> The current execution contract is defined by the [CDL reference](overall.md) and
> [language scope](overall.md#language-scope).

## 1. Support scope

`metadata` describes a resource's authorship, revision and classification. This
page covers annotations inside `rule`, `ruleset` and `pipeline` resources.

**The strict `cdl-core-risk-draft-1` profile rejects `metadata` with
`E_UNKNOWN_FIELD`**, including empty objects and `null`. The
[import authoring profile](import.md) validates the same resource shape after
resolution and also rejects it. Writing `version: "0.1"` does not enable metadata
at either entry point.

Compatibility parsing has the following behavior:

| Resource form | Current behavior |
|---|---|
| Rule and Ruleset | An omitted field stays absent. A present value is converted to a JSON value, including scalars, arrays and `null`; a failed conversion silently drops the entire metadata value. |
| Pipeline with `entry` or `step` wrappers | Reads a mapping. A non-mapping value is ignored; non-string keys and individual values that cannot convert to JSON are skipped. |
| Historical sequential Pipeline | Metadata is ignored. |

These differences are compatibility behavior. They do not provide a shared
validator or a guarantee that malformed annotations will be reported.

## 2. Authoring structure and field conventions

For compatible authoring across Rule, Ruleset and the Pipeline form above, use an
optional mapping with string keys. All entries are optional, and their order is
irrelevant. An empty mapping `{}` is allowed. Omit the field when no annotations
are needed; an explicit `metadata: null` is handled differently across resource forms.

Custom entries may use JSON-compatible strings, finite numbers, booleans, arrays,
objects and `null`. Use string keys in nested objects as well. `snake_case` is a
naming convention, and custom entries do not need to accompany any standard field.

The following are suggested meanings and value shapes, not parser-enforced
requirements. The compatibility parsers do not validate these names, types,
revision formats, timestamp formats or label vocabularies.

| Optional field | Suggested value | Meaning |
|---|---|---|
| `version` | String such as `"1.0.0"` | Revision label for this resource. It does not select a CDL language version or resolve dependencies. |
| `author` | String | Author or maintaining team. |
| `updated` | Quoted timestamp with a timezone, such as `"2025-12-20T10:00:00+08:00"` | Author-supplied update time. UTC or an explicit offset makes the time unambiguous. |
| `owner` | String | Responsible team or individual. |
| `category` | String | Classification used by external authoring tools. |
| `tags` | Array of strings | Labels for external search or grouping. |
| `environment` | String such as `"staging"` | Descriptive environment label. |
| `status` | String such as `"draft"` | Descriptive lifecycle label. |

The document's top-level `version: "0.1"` identifies the CDL language version;
`rule.metadata.version`, `ruleset.metadata.version` and `pipeline.metadata.version`
are independent annotations. None of these annotation fields is mandatory.

## 3. Meaning and preservation

Metadata entries do not change matching, scores, Rule order, Pipeline routing or
decisions. `status: deprecated` does not disable a resource, and `environment`
does not select a deployment. Adding metadata does not populate the expression
namespaces `event`, `sys` or `results`.

The author or an external authoring tool maintains the annotations. The parser
and compiler do not generate an author, increment a revision or update a timestamp.

Accepted annotations are retained in the parsed compatibility resource. Current
Rule, Ruleset and Pipeline compilers do not copy this user metadata into compiled
program metadata or decision Trace. Source annotations are distinct from the
execution metadata generated by the compiler. Consumers that need the annotations
must retain the source or parsed resource; compilation does not preserve them for
runtime inspection.

## 4. Examples and strict rejection

Each example below is a complete resource accepted by its compatibility parser.
A complete collection additionally requires a [Registry](registry.md) and a separately
supplied [input Schema](schema/input.json). Metadata remains unsupported by strict Core.

### Rule with revision information

```yaml
version: "0.1"
rule:
  id: large_amount
  name: Large amount
  when: event.amount > 1000
  score: 60
  metadata:
    version: "1.0.0"
    author: "Risk Team"
    updated: "2025-12-20T10:00:00+08:00"
```

### Ruleset with only custom annotations

This example deliberately omits `version`, `author` and `updated` inside metadata.

```yaml
version: "0.1"
ruleset:
  id: risk
  rules:
    - large_amount
  conclusion:
    - when: total_score >= 60
      signal: decline
    - when: total_score > 50
      signal: review
    - default: true
      signal: approve
  metadata:
    owner: "fraud_team"
    category: "payment"
    tags: [fraud, payment]
```

### Pipeline with descriptive labels

```yaml
version: "0.1"
pipeline:
  id: payment
  name: Payment risk
  entry: check
  steps:
    - step:
        id: check
        name: Check risk
        type: ruleset
        ruleset: risk
        next: end
  decision:
    - when: results.risk.signal == "decline"
      result: decline
      actions: [BLOCK]
      reason: Large amount
    - when: results.risk.score > 50
      result: review
      actions: [REVIEW]
    - default: true
      result: approve
      reason: Below threshold
  metadata:
    environment: "staging"
    status: "draft"
```

Strict validation rejects each resource at stage `validate` with
`E_UNKNOWN_FIELD`, at `/rule`, `/ruleset` or `/pipeline` respectively. Removing
only `metadata` makes each resource valid and allows compilation with the rest
of the payment example.

Compatibility parsing and strict admission are separate: acceptance by a compatibility
parser does not enable metadata in Core or preserve it in compiled execution results.
